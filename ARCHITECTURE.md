# ARCHITECTURE.md — EnvSync (черновик этапа 0)

Статус: **черновик, ждёт одобрения** (критерий готовности этапа 0). Кода пока нет.

## 1. Цель

Две Windows 11 машины (ПК и ноутбук) с одинаковой средой, которая синхронизируется сама,
в обе стороны, почти в реальном времени. Если машина выключена, изменения копятся и
применяются при следующем включении.

Синкается: файлы и папки (с перемещениями и переименованиями), одинаковые пути,
обои, тема, настройки Windows и приложений, набор программ.
Не синкается: см. `docs/not-synced.md` (черновик ниже, раздел 8).

Это личный проект. Мультипользовательской инфраструктуры нет, но пути, имя пользователя
и имена машин в код не зашиваются.

## 2. Принятые решения

| Вопрос | Решение | Причина |
|---|---|---|
| Файловый движок | Syncthing в MVP, как внешний процесс, управление через REST API и events | Зрелый движок, низкий риск потери данных; свой движок откладывается |
| Язык | Go | Один `.exe`, нативный реестр, тот же язык, что у Syncthing; позже можно писать свой движок без смены стека |
| Режим | Чистый P2P поверх Tailscale | VPS не нужен для старта; архитектура не запрещает релей позже |
| `.git` | Не синкаем | Параллельные правки ломают репозиторий; репозитории разводятся через `git push/pull` |
| Профиль | Синкаем целиком, с исключениями | Решение владельца |
| Пути | Буквы дисков и пути одинаковые; эталон — ПК владельца | Решение владельца |
| Манифест | Приватный git-репозиторий (источник истины) | История изменений и простой откат |
| Интерфейс | Трей + CLI + локальный веб-интерфейс на localhost | Веб-интерфейс хочет владелец |
| Запуск агента | Задача планировщика при входе пользователя, не служба | HKCU, обои и тема живут в пользовательской сессии; служба нужна только админ-хелперу |

## 3. Компоненты

```
 Машина A                                   Машина B
 +--------------------------------+         +--------------------------------+
 | envsync agent (Go, user session)|        | envsync agent (Go, user session)|
 |  - core: манифест, журнал,     |         |  - core: манифест, журнал,     |
 |    конфликты, откат            |         |    конфликты, откат            |
 |  - modules: files, settings,   |         |  - modules: files, settings,   |
 |    appearance, software        |         |    appearance, software        |
 |  - web UI (localhost) + трей   |         |  - web UI (localhost) + трей   |
 |  - Syncthing (дочерний процесс)|<------->|  - Syncthing (дочерний процесс)|
 +--------------------------------+ Tailscale +------------------------------+
                                   (шифр., P2P)
 Манифест envsync.yaml — в приватном git-репозитории.
```

- **Агент** — один процесс на машину, запускается при входе пользователя.
- **Syncthing** — отдельный процесс под управлением агента. Слушает только интерфейс Tailscale.
- **Модули** — плагины с единым интерфейсом: `Scan`, `Diff`, `Plan` (dry-run), `Apply`, `Rollback`.
- **Админ-хелпер** — отдельный повышенный процесс для HKLM и установки программ. По умолчанию выключен, добавляется последним.

## 4. Как синкаются разные вещи

**Файлы.** Папки из манифеста отдаются Syncthing. Исключения (кэши, `node_modules`,
сборочные папки, `.git`, служебная папка агента) — через `.stignore`, который генерируется из манифеста.
Перемещения Syncthing видит как «удалить + создать», но блоки берёт из локальных данных,
поэтому повторной передачи нет. Конфликты сохраняются как `.sync-conflict-…`, версии и
корзина — через встроенное версионирование. Резерв места под историю: +30–50 % к объёму данных.

**Настройки, оформление, программы.** Каждая машина экспортирует декларативное состояние
своей части в служебную папку, которая синкается через Syncthing. Вторая машина читает
состояние, строит dry-run и применяет после подтверждения. Каждая машина пишет только
свою часть, поэтому циклов «A → B → A» нет; у каждой операции есть метка происхождения.
Настройки и реестр: побеждает последняя правка, всё пишется в журнал и откатывается.

**Реестр.** Только белый список ключей из манифеста, в первую очередь HKCU. Тип значения и
признак «применится сразу / нужен перезапуск проводника» указываются для каждого ключа.
Список ключей составляется по документации и проверкой на реальной системе Windows 11, не по памяти.

**Программы.** Желаемый набор — в манифесте, установка через `winget`. Новая программа на
одной машине предлагается к добавлению в манифест. Удаление — только по явному подтверждению.

**Адаптеры приложений.** По одному на программу (редактор, терминал, браузер, мессенджеры,
git, Claude). Каждый знает, какие файлы брать, что исключить (кэши, сессии, токены) и как
понять, что программа запущена. Каждый проходит тест «применил → проверил → откатил».
Точный список программ и состав конфигов Claude уточняются к этапу 4.

## 5. Манифест (`envsync.yaml`)

Содержит: версию схемы; состав синка (папки, исключения, ключи реестра, программы);
профили машин (переопределения по имени машины); переменные путей `{{user}}`,
`{{sync_root}}`, `{{appdata}}`. Что в манифесте не написано, агент не трогает.
Пример без личных данных — `envsync.example.yaml` (появится на этапе 3).

## 6. Безопасность и защита данных

- Никакого стирания при конфликте: обе версии сохраняются.
- Любое изменение живой системы — сначала dry-run и подтверждение.
- Снимок отката перед каждым применением настроек (выгрузка веток реестра и конфигов).
- Предохранитель массового удаления: порог из манифеста (например > 5 % данных или > 1000 файлов) — агент ставит папку на паузу и ждёт подтверждения.
- Секреты (пароли, токены, ssh-ключи, данные браузеров) по умолчанию не синкаются.
- Шифрование и сопряжение: используем готовое (TLS Syncthing по ID устройств, Tailscale). Своей криптографии нет.
- Кнопка «пауза всего» и команда `envsync rollback`; журнал аудита в человекочитаемом виде.
- До этапа 6 агент работает только с тестовыми папками. Реестр — только после экспорта ветки.

| Пользователь | `kiyoushii` | `kiyoushii` |

| Инструменты | есть `winget`, `git`; нет `tailscale`, `syncthing`, `go` | не замерено |

Выводы:
- Имя пользователя и путь профиля совпадают, буква диска одна (`C:`): проблемы с разными путями нет, junction для выравнивания пока не нужны.
- Профиль ПК без `AppData` около 45 ГБ (`Downloads` 20 ГБ, `.ollama` 10,5 ГБ, `Desktop` 5,3 ГБ, `.pico-sdk` 2,1 ГБ). `AppData` весит 116,7 ГБ, это в основном то, что синкать не нужно; разбор — открытый пункт.
- Запас на историю версий (+30–50 %) помещается на обоих дисках, если `AppData` исключить почти целиком. Свободного места на ПК меньше всего (108,8 ГБ): это ограничивающий фактор.
- На ПК редакция Pro, поэтому Windows Sandbox/Hyper-V, вероятно, можно включить для тестов; проверим к этапу 4.

Открыто:

Решения владельца по крупным папкам:
- `.ollama` (10,5 ГБ): владелец удаляет у себя целиком (вручную, агент ничего не удаляет). Путь остаётся в исключениях по умолчанию.
- `Downloads` (20 ГБ): синкаем, но сначала владелец вручную просматривает и чистит. В исключения добавляем незавершённые загрузки (`*.crdownload`, `*.part`, `*.tmp`).
- Замер профиля и инструментов на ноутбуке, его редакция Windows.
- Решить, нужно ли синкать `Downloads` и `.ollama` (модели).
- Список приложений для адаптеров и состав конфигов Claude — к этапу 4.

### AppData: политика по умолчанию (по замеру на ПК)

`AppData` — 116,7 ГБ, почти всё это не конфиги. Решение: **`AppData` целиком не синкается
по умолчанию, в синк попадают только файлы, явно разрешённые адаптером приложения** (белый список).

| Что лежит | Примеры (ГБ) | Политика |
|---|---|---|
| Временное и кэши | `Local\Temp` 27,5; `Local\Microsoft` 3,5; `npm-cache`, `pip`, `D3DSCache` | Исключить |
| Установленные программы | `Local\Programs` 13,4 (программы пользователя), `Local\Packages` | Не копировать; ставим через `winget` |
| Игры и лаунчеры | `AlbionOnline` 7,4; `.minecraft` 4,7; `majestic-launcher` 2,9; Steam, Epic, Riot | Исключить |
| Docker/WSL/модели | `Local\Docker` 8,2; `Local\Ollama` 1,7; `Roaming\open-webui` 2,4 | Исключить (образы и данные восстанавливаемы) |
| Сессии и токены | `Roaming\Telegram Desktop` 2,6; `discord`; `Spotify`; Яндекс Браузер | Исключить; вход заново, браузер — через аккаунт |
| Мелкие конфиги, кандидаты в адаптеры | `Roaming\Code`, `obsidian`, `DBeaverData`, `Antigravity IDE`, `gemini-desktop`, `.claude` | Адаптеры по одному, этап 4 |
| Данные приложения Claude | `Local\Claude-Data` 15,5 (по README внутри: настройки, вход в аккаунт, задачи Cowork и их файлы) | Исключить навсегда; не трогать, не перемещать и не удалять. Возможный адаптер на этапе 4 — только для настроек, не для этой папки |

Следствие: реальный объём синка — профиль без `AppData` (~45 ГБ), а после решений по
`Downloads` и `.ollama` — порядка 15–25 ГБ плюс небольшие конфиги приложений.

## 8. Не синкается (черновик)

Драйверы, разрешение/DPI/яркость, профили Wi-Fi и Bluetooth-сопряжения, лицензия Windows,
состояние запущенных программ, данные, зашифрованные привязкой к машине, Program Files,
кэши, временные файлы, игры. Обход: профиль машины, список программ, чек-лист ручной настройки.

## 9. Структура репозитория

```
cmd/envsync/            агент и CLI
internal/core/          журнал, манифест, переменные путей, конфликты, откат
internal/modules/       files, settings, appearance, software
internal/transport/     настройка Syncthing, сопряжение, Tailscale
internal/ui/ + web/     локальный веб-интерфейс, трей
scripts/                замер объёма (только чтение), установка
tests/                  интеграционные и хаос-сценарии
docs/                   чек-лист ручной настройки, список «не синкается»
```

## 10. Этапы

0 план → 1 сеть и сопряжение (сокращён: Syncthing + Tailscale) → 2 файловый MVP →
3 манифест и профили → 4 настройки и оформление → 5 программы → 6 безопасность и откат →
7 интерфейс (веб + трей) → 8 VPS (опционально) → 9 установщик.
Следующий этап не начинается без выполненного критерия и вашего «дальше».

Автозапуск агента (задача планировщика при входе) и проверка перезагрузки сделаны частью этапа 9:
до тех пор `envsync run` запускается вручную.
