# Этап 4 — настройки и оформление

Статус: **выполнен в части кода и тестов** (11.11.2026). Применение к настоящей системе ПК и ноутбука
сознательно не делалось без отдельной проверки, см. «Что осталось». Ветка `stage-4-settings` (от `stage-3-manifest`).

## Цель и критерий

Темы, обои, проводник, региональные форматы и конфиги приложений синхронизируются между машинами по принципам
из плана: белый список, dry-run, снимок «до», откат, ничего не удаляется. Критерий из плана: **каждый адаптер прошёл цикл
«применил → проверил → откатил» на тестовой машине**.

## Как это работает

Каждая машина раз в запуск делает `envsync settings export`: снимает состояние каждого модуля в файл
`state/<машина>/<модуль>.json` (и файлы-приложения вроде картинки обоев в `state/<машина>/assets/<модуль>/`).
Папку `state` синкает Syncthing как служебную папку `envsync-state`. Вторая машина:

1. `settings plan` — берёт у других машин самое свежее состояние модуля, если оно **новее её собственного**, и показывает dry-run;
2. `settings apply` — после подтверждения делает снимок «до», применяет, пишет журнал и сразу фиксирует новое состояние как своё;
3. `settings rollback` — возвращает всё, что изменил запуск (в обратном порядке модулей).

**Первый снимок — база.** Самый первый снимок машины не считается правкой (нулевое `ChangedAt`), иначе машина, запустившая агент позже,
навязала бы свои настройки остальным. Первичное выравнивание с эталоном явное: `envsync settings apply --from DESKTOP-LS890QQ` (уточнено на этапе 9).

**Двусторонний синк с подтверждением на эталоне** (решение владельца после этапа 9). Агент раз в минуту снимает настройки и:
- на машине с `envsync settings auto on` (ноутбук) сам применяет более свежие настройки других машин, со снимком и откатом;
- на машине без него (ПК, по умолчанию) считает, сколько изменений с других машин ждут решения: число видно в статусе, на вкладке
  «Настройки» интерфейса (кнопки «Применить» и «Оставить как здесь») и цветом значка в трее. «Оставить как здесь» делает вариант этой машины
  самой свежей правкой, и машины с автоприменением возвращаются к нему.

**Нет циклов «A → B → A».** Каждая машина пишет только свою подпапку. Состояние перезаписывается, только если данные
изменились (`ChangedAt` не двигается от повторного снимка), поэтому применённое на B выглядит у A как «то же самое»,
а не как новое изменение. **Побеждает последняя правка** (по `ChangedAt`); локальная правка новее удалённой не затирается.

## Модули

| Модуль | Что синкается | Вступает в силу |
|---|---|---|
| `appearance` | тёмная/светлая тема приложений и системы, прозрачность, акцентный цвет и палитра | сразу (рассылается `WM_SETTINGCHANGE`) |
| `wallpaper` | сам файл картинки (едет с состоянием) и режим подгонки; стандартные обои Windows передаются только путём | сразу |
| `explorer` | расширения файлов, скрытые файлы, «открывать в», выравнивание и кнопки панели задач, поиск | после перезапуска проводника |
| `regional` | форматы даты и времени, первый день недели, повтор клавиш | после выхода из системы |
| `appconfig` | git, VS Code (настройки, клавиши, сниппеты), Windows Terminal, Claude (CLAUDE.md, commands, agents, skills) | сразу |

Белые списки ключей реестра составлены по документации и сверены чтением реальной Windows 11 (сборка 26200): типы
подтверждены, значения, которых по умолчанию нет (`LaunchTo`, `TaskbarAl`), передаются как «нет значения» и при применении
удаляются. Список — в `internal/modules/winreg/specs.go`; добавить настройку = добавить строку.

## Защита данных

- **Белый список**: что не перечислено, агент не читает и не меняет. Желаемое состояние с чужим ключом или чужим типом отклоняется.
- **Снимок «до»** сохраняется до первой записи; сбой на середине применения откатывает весь запуск (все модули).
- **Ничего не удаляется**: `appconfig` только создаёт и заменяет файлы; при откате удаляются только файлы, созданные самим применением.
- **Секреты не синкаются**: файл, похожий на секреты (токены, пароли, закрытые ключи, `apiKey`), в состояние не попадает и не
  копируется в папку, которая едет по сети; причина записана в состоянии. Claude: берём только `CLAUDE.md`, `commands`, `agents`,
  `skills`; не берём `settings.json`, учётные данные, историю, сессии и `skills/synced` (его ведёт сам Claude через аккаунт).
- **Приложение запущено**: адаптер может объявить процессы; пока они работают, конфиг пропускается с пояснением в dry-run.
- **Ключи из чужого состояния не доверенные**: выход за пределы папки (`..`) и неизвестные корни отклоняются.
- **Журнал аудита** `journal.jsonl` в человекочитаемом виде: `envsync settings journal`.
- Агент **не перезапускает проводник** и не выходит из системы сам, только подсказывает.

## Проверки

- Движок: «побеждает последняя правка», нет пинг-понга, локальная правка новее не затирается, откат запуска, откат всех модулей
  при сбое одного, проблема одного модуля не останавливает остальные.
- `winreg`: цикл «применил → проверил → откатил» (создание, изменение, удаление значения, возврат), частичный сбой записи, белый список,
  проверка типов; **на настоящем реестре** на собственных тестовых ключах `HKCU\Software\EnvSyncTest\...` (создаются и удаляются тестом).
- `wallpaper`: картинка едет между «машинами», режим подгонки из профиля машины, одна и та же картинка в другом месте не изменение,
  стандартная картинка не копируется, недокачанная картинка не применяется.
- `appconfig`: цикл на конфигах двух «машин», занятое приложение пропускается и применяется после закрытия, секреты, `..` в ключах, устаревшие копии.
- Интеграционный тест на двух настоящих Syncthing: состояние и файл-приложение едут через `envsync-state`, вторая машина строит план и
  применяет, обратно ничего не уходит, откат возвращает значения.
- Сухой прогон на реальной системе этого ПК (только чтение): `settings export` в изолированной папке, поддельная «вторая машина»
  с другими значениями и `settings plan`. План показал ровно ожидаемые изменения; реестр не менялся.

## Что осталось

- **Применение на настоящей системе** (`settings apply` на ПК и ноутбуке): сменит тему, режим подгонки обоев и т. п., поэтому требует отдельного
  подтверждения владельца. Откат при этом один командой. Виртуальной машины или Windows Sandbox для прогона нет (включение компонента
  требует прав администратора и перезагрузки).
- Не проверено на живой системе: перерисовка окон после смены акцента (`WM_SETTINGCHANGE`), реальный вызов смены обоев
  (`SystemParametersInfo`). Эти два места покрыты только подменой.
- Расширения VS Code (список и установка) и профили приложений вне белого списка: по одному, по мере надобности.
- Раскладки и языки ввода сознательно не включены: ошибка делает ввод неработоспособным.
- Положение иконок на рабочем столе: экспериментально, будет делаться после остальных этапов, без обещаний.
