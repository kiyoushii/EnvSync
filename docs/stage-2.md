# Этап 2 — файловый MVP

Статус: **выполнен** (11.11.2026), критерии подтверждены интеграционными тестами. Ветка `stage-2-files` (от `stage-1-network`).

## Цель

Файловый движок (Syncthing, по решению этапа 0) работает на тестовой папке так, как нужно проекту:
перемещения и переименования без повторной передачи данных, конфликты без потери, история версий,
исключения, устойчивость к обрыву связи, сложные имена файлов.

Принцип этапа: **своего движка не пишем**. Работа агента здесь — настроить Syncthing правильно
и доказать тестами, что он ведёт себя нужным образом. Всё, чего он не делает сам, фиксируем как
вывод для этапов 3 и 6.

До этапа 6 агент работает только с тестовой папкой, реальные данные не затрагиваются.

## Критерий готовности (из плана)

1. Папка, переложенная или переименованная на одной машине, оказывается на второй **без повторной передачи данных**.
2. Обрыв связи во время правки или передачи **не приводит к потере данных**: после восстановления связи содержимое совпадает по хешу.

Дополнительно проверяем (требования раздела 5.1 и 7 исходного плана): конфликты, история версий,
исключения, имена с кириллицей и пробелами, очень длинные пути.

## Что делаем в коде агента

| Что | Зачем |
|---|---|
| Исключения (`.stignore` через REST) из настроек агента | кэши, `node_modules`, `.git`, незавершённые загрузки, служебные папки не синкаются; список по умолчанию из `ARCHITECTURE.md` |
| Параметры папки в `pair` | быстрый отклик (`fsWatcherDelayS`), лимит конфликтных копий, версионирование «корзина» |
| Методы REST-клиента: пауза/возобновление устройства, статус папки, исключения, счётчики трафика | нужны агенту для статуса и тестам для проверок |
| Dry-run в `pair` показывает исключения и параметры | принцип «сначала показать, потом менять» |

## Тесты (интеграционные, на настоящих Syncthing на loopback)

| Сценарий | Что доказываем |
|---|---|
| Переименование и перемещение папки с крупным файлом | на второй машине путь изменился, переданных байт во много раз меньше размера файла |
| Одновременная правка одного файла на обеих сторонах (связь на паузе) | остаются обе версии: победившая и `*.sync-conflict-*`, ничего не потеряно |
| Удаление файла | копия уходит в `.stversions` на второй стороне |
| Обрыв во время передачи (остановка второго Syncthing, запуск снова) | файл доезжает, хеш совпадает |
| Перемещение + правка на разных машинах | оба изменения применяются |
| Исключения | `node_modules`, `.git`, `*.crdownload` не доезжают, обычные файлы доезжают |
| Кириллица, пробелы, длинный путь (больше 260 символов) | файлы доезжают с тем же содержимым |

## Результаты

Все сценарии выполнены интеграционными тестами на двух настоящих Syncthing (loopback), 95 секунд на весь набор.

| Сценарий | Итог |
|---|---|
| Перемещение + переименование папки с файлом 24 МБ | Второй стороне передано **7 КБ** (только индекс). Файл не передавался заново. Критерий 1 выполнен. |
| Обрыв связи: Syncthing на второй машине убит «жёстко» на середине передачи 32 МБ | После перезапуска файл доехал, SHA-256 совпал. Критерий 2 выполнен. |
| Конфликт: разные правки одного файла при разорванной связи | Остались обе версии на обеих машинах: победившая (более новая) и `doc.sync-conflict-…txt`. |
| Удаление файла | Копия лежит в `.stversions` на второй машине. |
| Исключения (`.git`, `node_modules` на любой глубине, `Cache`, `*.crdownload`, `*.part`, `Thumbs.db`, `~$*`) | Не доехали, исходные файлы на месте; обычные файлы доехали. |
| Кириллица, пробелы, юникод, имя из 120 символов, путь длиннее 300 символов | Доехали с тем же содержимым. |
| Перемещение на одной машине + правка на другой | См. ограничение ниже. |

### Ограничение движка (важно для этапов 3 и 6)

Одновременное «переместил файл на A» и «изменил его на B» Syncthing сводит **без потери данных, но не в один файл**:
правка сохраняется в старом месте (`x/one.txt`), на новом месте остаётся старое содержимое (`y/one.txt`).
Исходное требование «оба изменения должны примениться» выполнено в части «ничего не потеряно», но не в части
«файл на новом месте с новым содержимым». Свой движок ради этого писать не будем: случай редкий, данные целы,
пользователь видит обе копии. Если понадобится, решается отдельным шагом поверх (сверка по хешу в журнале агента).

### Служебное

- Исключения хранятся в `.stignore` в корне синкаемой папки и **между машинами не синкаются**: каждая машина применяет свои
  через `envsync pair`. Это сделано намеренно: список общий, но держится в манифесте (этап 3), а не в синкаемых данных.
- Предохранитель массового удаления не входит в этап 2 (этап 6).
